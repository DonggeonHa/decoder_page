# 검증 결과 — 2026-09-08

## 최신 변경 — 로컬 TXT 저장 / 대용량 클립보드 안내

- 사용자 화면의 Output 크기 3,221,754 chars와 클립보드 실패 알림을 근거로, 서버 전송 없는 UTF-8 TXT 다운로드를 추가했습니다. 실제 사용자 로그는 테스트에 사용하지 않았습니다.
- 기존 코드가 3,221,754자의 합성 원문을 OS 클립보드 API로 보내는 것을 브라우저 테스트에서 먼저 확인하여 실패(red)를 재현했습니다. Android OS 자체를 재현한 테스트는 아닙니다.
- 20만 UTF-16 code units 초과는 클립보드 호출 없이 TXT 저장으로 안내합니다. 작은 원문도 API 응답만으로 복사 성공을 단정하지 않습니다. 이 기준은 UI 보호 정책이지 OS의 정확한 한도가 아닙니다.
- `TXT 저장`은 내부 복원 문자열로 Blob을 만들고 다운로드합니다. 서버 업로드, 자동 클립보드 읽기, 원문 BOM 추가/제거, 줄바꿈 변환은 없습니다. 페이지는 저장 완료 대신 다운로드 요청과 파일 확인을 안내합니다.
- `npm test`: Node/Java 8 core harness 포함 21개 통과.
- `npm run test:browser -- --decoder-only`: 기존 조각 수집/중지/재개/붙여넣기 및 BOM/CRLF 복사 회귀 검사 통과. 카메라/OS 클립보드는 대체 입력입니다.
- `npm run test:export`: 실제 headless Edge의 모바일 크기 뷰포트에서 다음 항목을 확인했습니다. GZIP 해제, DOM, Blob, object URL, 다운로드 스트림은 실제 브라우저 동작이고 OS 클립보드 경계만 대체했습니다.
  - 3,221,754자 합성 데이터: 클립보드 호출을 막고 TXT 다운로드 바이트가 원문과 일치.
  - 한글, 이모지, BOM, CRLF, 단독 CR, LF, 앞뒤 공백: 원본 UTF-8 바이트 그대로 저장. 작은 원문의 복사 경로 유지.
  - 클립보드 거절/미지원 상태에서도 TXT 다운로드 가능.
  - 200,000/200,001자의 복사 안내 경계 및 Clear 후 늦게 돌아온 복사 응답이 상태 문구를 덮어쓰지 않는지 확인.
  - 정확히 5,000,000 UTF-8 bytes의 한글 원문 다운로드가 바이트 단위로 일치.
  - 5,000,001 bytes 복원 거절 후 및 Clear 후 저장 버튼 비활성화. 이전 결과가 잘못 저장되지 않음.
  - 다운로드 object URL 지연 해제, 외부 전송 없음, 브라우저 예외 없음, 390px 폭에서 가로 넘침 없음. 합성 화면 스크린샷 직접 확인.
- 앱 진입 파일 버전은 `20260908-txt-export`입니다. QR 형식, JSP, 300장/5MB 한도, scanner/protocol/gzip 모듈은 변경하지 않았습니다.
- **실제 Android Chrome의 다운로드 관리 화면, 사용자 실제 263장 로그 파일, 저장공간/관리정책별 허용 여부는 미검증입니다.** 사용자는 다운로드 목록에서 파일 생성 및 내용을 확인해야 합니다. 구버전 탭 새로고침 시 수집한 QR은 사라집니다.

재실행은 Node, Java 8(`JAVA_HOME`), Playwright(`PLAYWRIGHT_MODULE`에 설치 경로 지정 가능), Edge가 필요합니다. `BROWSER_CHANNEL`로 테스트 브라우저 채널을 바꿀 수 있습니다. 운영 페이지에는 추가 의존성이 없습니다.

## 이전 변경 — 300장 / 5MB 동기화

- 사용자가 단독 사용 환경에서 JSP를 5,000,000 bytes / 300장으로 변경하고 263장을 생성했다고 보고했습니다. 실제 사용자 로그는 수집하지 않았습니다.
- 구버전 디코더에서 263장 헤더가 `Maximum QR count is 200.`로 거절되는 것과, 1MB 초과 해제가 중단되는 것을 합성 입력으로 재현했습니다.
- JSP와 디코더의 한도를 300장 / 5,000,000 UTF-8 bytes로 맞췄습니다. 한 장의 조각은 1,200자 그대로이며 RAW/GZ/GZQR v1 형식은 변경하지 않았습니다.
- 디코더에는 JSP를 거치지 않은 QR/붙여넣기도 들어올 수 있으므로, 큰 장수로 인한 수집 루프와 과도한 GZIP 해제로부터 브라우저를 보호하는 제한을 유지했습니다.
- 배포 파일의 버전 주소는 `20260908-300qr-5mb`입니다. 새로고침 후 '최대 300장 · 복원 최대 5MB' 안내를 확인하세요. 기존 263장 QR은 다시 생성할 필요 없이 새 디코더로 재스캔할 수 있습니다.

### 이번에 실제 확인한 범위

- Node의 실제 protocol/gzip/scanner 모듈을 메모리에서 실행한 테스트 20개 통과.
- 263장 헤더 허용 및 합성 GZIP 문자열 263개 조각의 역순 수집 → 원문 복원. 사용자 실제 로그 또는 카메라 광학 인식 시험은 아닙니다.
- 300장 역순 수집, 중복 무시, 누락 번호 유지, 301장 및 비정상적으로 큰 total 거절.
- 1MB를 넘는 한글 원문과 정확히 5,000,000 UTF-8 bytes 복원, 5,000,001 bytes 거절.
- BOM/CRLF 보존, 잘못된 UTF-8 거절, 기존 카메라 비동기 취소·종료 회귀 검사.
- Java 8에서 변경된 JSP 핵심 선언부를 메모리 컴파일하고 기존 core harness 1개를 실행했습니다. RAW/GZ/GZQR 복원, 공백, escaping, 원문·장수 초과 거절을 확인했습니다.
- 이번 실행은 읽기 전용 작업환경이어서 파일을 생성하지 않는 검사 방식으로 진행했습니다. 300장 PNG 전체 생성/탐색, 5MB의 실제 JSP POST, 실제 WAS 메모리/동시 부하, 휴대폰 전체 스캔은 이번 변경에서 다시 검증하지 않았습니다.

**300장 / 5MB는 사용자 설정에 맞춘 지원 상한이지, 모든 WAS·휴대폰에서 검증된 안전 최대치가 아닙니다.**

## 이전 200장 / 1MB 버전의 검증 기록

아래의 환경·측정값·이미지 개수는 이전 버전에서 실행한 기록이며, 최신 300장 설정의 검증 결과로 읽으면 안 됩니다.

## 적용 범위

- 운영용 JSP: Java 8, 기존 ZXing import 4개 유지. 추가 QR 라이브러리 없음.
- 원문 한도 1,000,000 UTF-8 bytes / 최대 200장 / 조각 1,200자 / 헤더 포함 payload 최대 1,500 bytes.
- RAW/GZ/GZQR v1 형식 유지. 기존 생성 JSP의 QR도 디코더에서 처리 가능.
- 픽셀 행 단위 기록, 단일 UTF-8 배열 재사용, 단일 순회 HTML escaping, 명시적인 메모리 PNG 출력.
- QR 흰 여백 4칸, 원본 420px 표시, 0.5/0.7/1/1.5초 재생, 번호 이동, 현재와 다음 두 프레임만 미리 준비.
- 디코더: 중지 후 수집 재개, 누락 번호 복사, 조각 붙여넣기, 선두 BOM/CRLF 복사 보존, 최대 해제 크기 검사, 늦게 끝난 카메라 요청/인식 무시.

## 실제 사용한 검증 환경

- Windows 홈서버, Temurin OpenJDK 1.8.0_492, Node.js 24.18.0.
- QR 검증용 ZXing core/javase 3.5.3.
- JSP 실행 검증용 embedded Tomcat 9.0.115 + ECJ 3.26.0, 127.0.0.1 임시 포트.
- 설치된 Microsoft Edge의 headless 브라우저.
- 검증용 JAR은 .test-deps에만 저장하며 Git 및 인트라넷 전달 대상에서 제외.

## 검증 항목

1. Node/Java 코어 회귀 테스트 17개: RAW/GZ 분기, 공백, BOM, 잘못된 UTF-8, 해제 크기, 중복/충돌/누락, 200장, 카메라 취소/종료.
2. Java 8: 800/801 byte RAW 경계, 6만 자의 압축이 잘 안 되는 입력, 정확히 200장 허용, 200장 초과 및 원문 100만 bytes 초과 거절, HTML escaping.
3. PNG 202개(단일 RAW/GZ 각 1개, 멀티 200개)의 모든 픽셀이 ZXing BitMatrix와 일치하는지 검사하고 payload 데이터 복원.
4. Java가 만든 5개 fixture를 실제 JavaScript 디코더로 복원. 선두 BOM/공백/한글/CRLF/마지막 개행과 역순 200개 조각 포함.
5. 실제 JSP GET/POST: 한글 포함 6만 자 요청 → 56장 생성, UTF-8 입력 유지, 420px 표시, 50번 이동, 속도 변경, 일시정지, preload 최대 3개.
6. 실제 브라우저 UI: 조각 1개 수집 → 중지 → 이어서 수집 → 복원, 누락 번호 복사, 조각 붙여넣기, Copy Output의 BOM/CRLF 유지.

## 중요한 카메라 검증 한계

202개 PNG 중 5개는 ZXing 기본 위치 탐색에서 인식에 실패했습니다. 그 5개는 기존 생성 함수가 만든 이미지와 픽셀이 완전히 같아 이번 픽셀 기록 변경으로 생긴 차이는 아닙니다. 위치를 알고 있는 이미지용 PURE_BARCODE 옵션에서는 데이터를 복원했습니다. 따라서 이 결과를 자동 탐색 202/202 성공 또는 휴대폰 인식률 100%로 해석하면 안 됩니다.

브라우저 검증에서는 카메라/BarcodeDetector 입력과 클립보드 전송만 테스트용으로 대체했습니다. 앱의 수집/재개/복원/UI는 실제 코드를 실행했습니다. 휴대폰의 광학 인식, 초점, 조명, 모니터 배율, 화면 전환 중 인식률은 실기기 확인이 필요합니다.

실제 인트라넷 WAS와 그곳에 설치된 ZXing 버전은 확인하지 않았습니다. 이 결과는 위 버전에서의 검증입니다. WAS/프록시 POST 제한도 별도입니다.

## 성능 측정

기존 기준 커밋: c3d4113dd5ba7999adfd2b2fccb4336f7b4f79be.

같은 1,200자 조각의 QR 20종으로 Java 8에서 각 버전 60장 워밍업 후, 20장씩 7회(총 140장/버전) 측정했습니다. 기존/개선 순서를 번갈아 실행하고 회차별 한 장당 시간의 중앙값을 비교했습니다.

| 측정 대상 | 기존 | 개선 |
|---|---:|---:|
| ZXing 인코딩 + 이미지 기록 + PNG + Base64 | 9.036 ms/장 | 5.693 ms/장 |

이 측정 구간은 약 37% 감소(처리 속도 약 1.59배)했습니다. GZIP, 전체 JSP 요청, 네트워크, 카메라 스캔을 포함한 속도가 아닙니다. 단일 홈서버의 합성 데이터 결과이며 실제 WAS에서 같은 개선율을 보장하지 않습니다.

## 재실행

검증 PC에 JDK 8과 Node.js를 준비하고 JAVA_HOME을 설정합니다. Java 8/ZXing 외의 아래 도구들은 테스트 PC에만 필요합니다.

```text
npm test
npm run test:deps
npm run test:java
npm run test:browser
node scripts/benchmark.mjs
```

브라우저 검증에는 테스트 PC의 Playwright 패키지와 Edge(기본값)가 필요합니다. PLAYWRIGHT_MODULE로 설치된 패키지 위치를, BROWSER_CHANNEL로 사용할 채널을 지정할 수 있습니다. npm run test:deps는 공식 Maven Central에서 검증용 JAR을 받고 체크섬을 대조합니다.

타이핑 가이드를 다시 만들려면 node scripts/build-typing-guide.mjs를 실행합니다. 가이드의 코드 블록은 검증된 완성 JSP에서 추출됩니다.
